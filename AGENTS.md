# AGENTS.md

This file provides guidance to coding agents (Claude Code, pi, …) when working with code in this repository.

**Everything in AGENTS.md must be extremely terse: bulleted lists, not paragraphs, as concise and token-efficient as possible.**

**Keep this file correct: update it when details change, and add genuinely important architectural decisions as they're made.**

**Code comments must be extremely terse too: short one-liners explaining *why*, never restating the code. No prose blocks, no redundant JSDoc.**

## Project state

- Scaffolded. Working vertical slice: launch Claude Code/pi sessions, stream live to xterm in the browser, type back, switch between concurrent sessions.
- TypeScript throughout. Tests use **Vitest** (`npm test`), co-located `*.test.ts` next to source, Node environment (`vitest.config.ts`). First coverage is the pure shared logic (`shared/chat.test.ts` reducer, `shared/render.test.ts`) — no DOM, no processes, no tokens. Test files are excluded from `npm run typecheck` (both tsconfigs) so that gate stays scoped to shipping code; Vitest runs them. Component tests (jsdom + Testing Library) and live smoke scripts layer on top later.
- **Prefer TDD when adding a new harness surface or normalized message type** — i.e. a new `ChatEvent` / `ChatAction` / `ChatUiRequest` kind, an adapter mapping a fresh SDK/harness signal, or a new agent interaction flow (permissions, dialogs, resume, compaction, plan-mode/`ExitPlanMode`, model/mode switches). These have a clean *observable backend contract* (the emitted events / folded `ChatState`) that a token-free `claude-local` `*.e2e.test.ts` can pin. Order: **draft the test first** against the intended contract → **implement** the adapter/protocol → **run it live and adjust the test** to what the real harness actually does (e.g. an empty `plan` field, messages the SDK does/doesn't replay) → **only then build the frontend**. Keep the deterministic assertion (our event surfacing) as the hard gate and any model-behavior check (recall, verbosity) as a softer secondary one.

## Commands

- `npm run dev` — single-process dev server (`tsx watch server/index.ts --dev`).
- `npm run build` — production frontend build to `dist/web` (Vite).
- `npm start` — run server serving the prebuilt `dist/web`.
- `npm run typecheck` — `tsc --noEmit` for web (`tsconfig.json`) + server (`tsconfig.server.json`).
- `npm test` — Vitest run (once, pure/fast — no processes/tokens); `npm run test:watch` for the watch loop. Excludes `*.e2e.test.ts`.
- `npm run test:e2e` — live end-to-end tests (`*.e2e.test.ts`, `vitest.e2e.config.ts`) that drive the real `claude-local` harness against vLLM; self-skip when claude-local is disabled/unreachable. Kept out of `npm test` (needs a running endpoint) — as is anything else that spawns processes, even the endpoint-free `manager-exit.e2e.test.ts` / `system.e2e.test.ts`.
- `npm run chat-log-report` — offline chat-render-log diagnostics (see chat render log below).
- Requires `config.json` (run `./config-gen.sh`); the agent CLIs (`claude`, `pi`) must be on `PATH`.
- Server is **never compiled** — `npm start` runs `tsx server/index.ts` directly. Only the frontend is built (`dist/web`).

## Deployment (systemd user service)

- **⚠️ NEVER run `./restart.sh`, `./rebuild.sh`, `./stop.sh`, or any `systemctl --user restart/stop agent-remote` yourself.** The agent (you) runs *inside* this application — restarting/stopping/rebuilding the service kills all live sessions, including your own. When a change needs to be picked up, **ask the user to run `./restart.sh`** themselves; never do it (or the rebuild) on their behalf.
- `./install-service.sh` — one-time: writes/enables `~/.config/systemd/user/agent-remote.service` (runs `npm start`), builds `dist/web` if missing, enables linger. User service (not system): agent CLIs live in per-user paths.
- `./start.sh` / `./stop.sh` / `./restart.sh` wrap `systemctl --user` as the canonical prod runner. `./restart.sh` rebuilds frontend then restarts.
- `./start.sh dev` is the exception: runs the `tsx watch` HMR server directly (pidfile + `setsid`, not systemd). `./stop.sh` prioritizes that pidfile if present, else stops the service.
- `./rebuild.sh` builds frontend only. Frontend change → rebuild + restart; server-only change → plain `systemctl --user restart agent-remote` (no build needed).
- **Restart resilience** (restart.sh used to leave the service dead; three compounding causes, all fixed — don't regress any):
  - `rebuild.sh` **stages + atomically swaps** (`vite build --outDir dist/web.next` → two `mv`s). Vite's `emptyOutDir` used to wipe `dist/web` under the live server for the whole build.
  - `serveStatic` (`index.ts`) **try/catches the read** → 503, and the server has `uncaughtException`/`unhandledRejection` log-and-continue handlers. A missing `index.html` mid-rebuild threw ENOENT out of an async handler and killed the process (and every live session). The SPA fallback path is not `existsSync`-checked, so it can always vanish under us.
  - `restart.sh` runs the rebuild+restart in a **transient unit** (`systemd-run --user --collect --unit=agent-remote-restart`) so it's outside the cgroup systemd is tearing down — the caller is normally an agent session *inside* the service, so an inline build gets killed half-way. It also verifies the unit came back and re-`start`s it if not. Falls back to inline when systemd-run/the unit is absent. (This is why `nohup ./restart.sh` used to be needed; it isn't now.)
  - Unit has `Restart=always` + `StartLimitIntervalSec=0` (default 5-starts/10s budget let a crash-loop wedge it dead permanently) + `TimeoutStopSec=20`.

## Layout

- `shared/protocol.ts` — WS message + session types, shared by both sides. Harness-agnostic. Also `CommandListing` (the `/api/commands` response shape), `SessionEvent` (command-start/end + cwd events), `FileEntry`/`DirListing`/`FileContent` (the file-editor `/api/files` + `/api/file` shapes), and the normalized chat schema (`SessionUi`, `ChatState`/`ChatMessage`/`ChatPart` — incl. the `image` part variant, `ChatEvent`, `ChatAction` — `prompt` carries optional `images:ChatImageRef[]`, `ChatUiRequest`/`ChatUiOption`, `ChatImageRef`, `ChatCapabilities`/`RewindPreview`, `AutoPrompt`/`ContinuityNewSession`, `AgentRun`). **Card options are structured** (`ChatUiOption {value,label,detail?,intent?}`): `value` is the stable id round-tripped in `ui-response.value` and matched by the adapter, `label`/`detail` are display-only (so a harness can enrich button text without breaking the decode), and `intent` (`accept`/`always`/`reject`/`cancel`) carries the semantics so `ChatView` and `assistant.ts` never pattern-match on label strings (AI-mode picks `accept`, never `always`).
- `shared/chat.ts` — `applyChatEvent` reducer folding `ChatEvent`s into `ChatState`; run identically by server (replayable per-session state) and client (live updates). Caps: 200 messages, 20k/tool output, 20 notices, 30 sub-agent runs. The only *destructive* fold is `rewind` (see below) — everything else appends/patches.
- **System turns (`ChatMessage.role: "system"`).** A turn the conversation *received* but neither party authored — a background-task notification, a peer/channel message. It's part of the transcript (it's what the agent replied to) but must never be attributed to the user. Renders as a muted centered line in transcript order (`.chat-system`, same idiom as `.chat-notice`); folded by the ordinary `user-message` event, which for `role:"system"` **skips clearing `promptSuggestions`/`autoPrompt`** — a notification is not the developer replying, and must not spend Continuity Mode's armed prompt. `suggestions.ts` labels it `System:` (never `Assistant:`, or the model reads machine output as its own words).
  - **The dangerous half is rewind, not the misattribution.** The claude CLI injects these as `user` entries with prose, indistinguishable from a prompt unless you check provenance. Counting one as a prompt desynchronizes `promptIds` from `promptUuid`'s positional fallback, and a rewind then forks the session at the *wrong* turn. Hence: system turns never enter `promptIds`/`promptUuids`, and the positional filter applies the same predicate.
- **Notices (`ChatNotice`) are ANCHORED, not pinned.** Compaction boundaries, harness errors, rewind confirmations: diagnostic (no render log, not rebuilt on resume — so not a `ChatMessage`) but part of the conversation's narrative, so the reducer stamps each with `anchorMessageId` (the streaming turn, else the last message) exactly like `AssistantTrace`, and `ChatView`'s `inlineAfter(messageId)` emits traces+notices together sorted by `at` after that turn. They used to render as the last 3 in a block *below* the whole transcript, so a `/compact` or resume line sat at the bottom while every later turn slid in above it. Same two consequences as traces: `inlineAfter(undefined)` leads (a notice that predates every message — session start), and **nothing renders after the last message** — a notice whose anchor aged out of the 200-message cap goes with it, and `rewind` prunes anchored ones while keeping unanchored. All 20 are shown now, not 3: inline they're history, and dropping the middle ones would leave gaps.
- **Sub-agent runs (nested chat sessions).** A tool call that spawns an agent (claude's `Agent`/`Task`) carries its whole nested conversation in `ChatState.agents[toolId]` (`AgentRun {toolId, agentType?, description?, state: ChatState, loading?}`). Three envelope events — **`agent-start`** (create/merge metadata, idempotent: a repeat never resets a live transcript), **`agent-event {toolId, event}`** (fold `event` into that run's `state` via `applyChatEvent` *recursively* — no second copy of the streaming/part-delta/tool-matching logic), **`agent-done {toolId, report?}`** (clear `loading`; append `report` as a final bubble unless the transcript already ends with it). Design rules that are load-bearing:
  - **The map is FLAT and root-only.** A depth-2 agent gets its own top-level entry keyed by a toolId that happens to live inside a depth-1 nested transcript; the renderer looks up the same root map, so arbitrary depth needs no recursive data shape and the reducer never searches nested states for a key. A nested `state.agents` stays `{}`.
  - **`rewind` prunes it transitively** (`reachableAgents`): BFS the surviving root messages' tool parts, then those runs' own tool parts. Same spirit as the `assistantTraces` prune.
  - **An empty run falls back to the ordinary tool view** (both `renderPart` and `ChatView`'s `ToolPart`), never an empty panel — a backgrounded agent's tool output is a "launched successfully" stub, which is the only information there is until its text arrives. `loading` is the one empty state that renders a panel ("Loading transcript…").
- `shared/render.ts` — single source of truth for turning a `ChatPart`/`ChatMessage` into displayed HTML (`renderPart`/`renderMessage`, plus the `md`/`escapeHtml`/`argsPreview`/`toolGlyph`/`truncate` primitives). `ChatView.tsx` imports the primitives so the UI can't drift from what's logged; `server/chatLog.ts` calls `renderMessage` to capture what's shown. Imports `marked` — keep it imported only by `ChatView` on the web side so it stays in the lazy chunk.
  - **User turns render markdown too**, not escaped plain text — prompts routinely carry lists, code spans, paths and pasted snippets, and the same `renderMarkdown` escapes raw HTML. Applied in all four user-bubble sites (`renderMessage`'s user branch + `renderAgentPanel`'s opening prompt; `ChatView`'s `Bubble`, `AgentPanel` prompt and queued prompts), each wrapping the text in `.chat-md`. Two CSS consequences: `.chat-bubble.user` needs `white-space: normal` (markdown owns its whitespace — `pre-wrap` would double every block gap, same rule assistant bubbles already had), and its nested `code`/`pre`/cells can't use `--raised` (the bubble is an *accent-tinted* fill, not `--panel`, so `--raised` is no longer a step up) — they tint off the bubble's own fill via `color-mix(… var(--text) 12%, transparent)`.
  - **Copy button** (`ChatView`'s `CopyButton`): floating, hover/focus-only, top-right of every user bubble and finished assistant prose bubble (not tool bubbles, not while streaming). Copies `copyText(parts)` (`render.ts`, pure/tested): raw markdown, thinking only if nothing else, images as `[image: name]`. `writeClipboard` falls back to `execCommand` — `navigator.clipboard` is absent over plain-http LAN access.
  - **Tool-call display** is driven by `toolView(part)` (field-driven, harness-agnostic — covers claude's `Edit`/`Read`/`Write`/`Bash` and pi's lowercase `read`/`write`/`bash` by looking at `file_path`/`path`, `command`, `old_string`/`new_string`, `content`, not tool names): returns a `{primary, secondary?, body}` display model. Summary shows a legible subject (`shortenPath` → `…/dir/file.ts`, or the command) not raw JSON; body is a Git-style diff for edits, a code block for Write/Bash content, path+range for Read, or pretty JSON for unknown tools. Both `renderPart` (HTML) and `ChatView`'s `ToolPart` (JSX) consume `toolView` so they can't drift. Tool bodies use `white-space: pre` + horizontal scroll (mobile pans, never wraps per-column). **An assistant turn renders as a *column of bubbles*, not one** (`groupParts` in `render.ts`, consumed by both `ChatView`'s `Bubble` and `renderMessage`): consecutive prose parts share a bubble, each tool call is its own (`.chat-tool.standalone` — `--panel` fill + `--r-lg`, i.e. bubble weight, with `overflow:hidden` clipping its full-bleed bodies). A turn is nearly always all prose or all tool, and the old single-bubble layout made the common tool-only turn a raised card inset inside a near-empty bubble; a mixed turn now just yields several bubbles. Nested `.chat-tool` (raised card, `--r-sm`) survives for the permission card, which is why `standalone` is a modifier rather than a change to the base rule. **This is presentation only** — grouping happens at render time, never in the reducer, since `ChatMessage.id` is load-bearing for rewind (`promptIds`), `AssistantTrace.anchorMessageId`, the `chat_render_log` key, and the streaming→finalized handoff. Prose groups key off their first part's index, tool groups off `toolId` so `<details>` open state survives a growing turn. Empty `thinking` parts (claude never streams reasoning) render as a transient pulsing "Thinking…" label and are stripped by the `shared/chat.ts` reducer (`dropEmptyThinking`) once the next part starts or the turn ends.
  - **Diff display model**: `ToolBody {kind:"diff", path?, rows:DiffRow[], added, removed}` + `ToolView.stat?` (the collapsed `+N −M`, rendered by both `renderPart`'s summary and `ChatView`'s so the render log matches the UI). `DiffRow = {kind:"line",line} | {kind:"fold",count?}` — consumers never re-derive folding. Pipeline: `editPairs()` (field-driven, so claude's `old_string`/`new_string` and pi's `edits[]:{oldText,newText}` both yield hunks; an empty side is a pure insertion/deletion) → `pairLines` → `lineDiff` (minimal LCS) → `markWordDiff` (token-level `.diff-word` marks inside changed pairs) → `diffRows` (elide unchanged runs into `.diff-fold` rows, `DIFF_CONTEXT = 4`). Folding is applied **per hunk**, and a hunk break row is only pushed when no fold already borders the join (two adjacent `.diff-fold` rows are noise). Three guards against folding too much: a diff with no changed lines at all, a fragment ≤ `context*4` lines, and a hidden run of <2 lines all stay fully visible. No line numbers — `old_string` carries no file offset, so any gutter number would be a lie. `.diff-fold` deliberately gets no red/green bar (see styles).
  - **Thinking amount** (`thinkingSummary(text, live?)` → `{label, amount}`): collapsed thinking shows how long the thought was, words until `WORDS_PER_PAGE * PAGES_FROM` (500 × 1.2) then pages with one decimal (`Thought for 420 words`, `Thought for 2.0 pages`). `live` swaps the label to "Thinking…" for the part still being streamed — `ChatView` passes it only for the last part of the last group, never for finished prose.
  - **A tool call with a sub-agent run expands into that agent's own chat session** (`.chat-agent`, rendered by `renderAgentPanel` / `ChatView`'s `AgentPanel`) *instead of* its args JSON and its `<pre>` output — the sub-agent's answer is already the last nested bubble, so the `<pre>` would just duplicate it. Same `Bubble`/`groupParts`/`ToolPart` path as the main transcript, so it nests recursively. **The panel opens with the task the agent was given** (`agentPrompt(part)` — the tool's own `args.prompt`), because *neither* path carries the sub-agent's first user message: the live stream doesn't forward it and `getSubagentMessages` drops it as the sidechain root (verified). Render-time synthesis, never in the reducer — same rule as `groupParts`. The panel is **`max-height:50vh` with its own scroll** — an agent run is a whole conversation and must not push the main transcript off-screen — and pins to the bottom while the parent tool is still running (independent of `.chat-scroll`'s stickiness). As the panel itself grows (up to the cap), `useKeepBottomInView` (a ResizeObserver) scrolls its container so the panel's bottom stays in view — only if that bottom edge was already visible, by at most the growth, and never past the panel's top. Needed because a peer panel grows on *another* session's events, which the outer stick-to-bottom never sees. Elevation: the panel sits on the tool bubble's `--panel`, so its own bubbles/tools step up to `--raised` (no fourth surface needed — tool bodies already `color-mix` off `--raised`), and nested tool bodies drop from 40vh to 20vh so they can't fill the panel. `ChatView` threads the run map through an **`AgentsContext`**, not props: `ToolPart` → `Bubble` → `ToolPart` nests arbitrarily deep. Expanding a `<details>` whose run is an empty stub fires the `load-agent` action (see resume, below).
- `server/` — Node backend. `config.ts` (loads `config.json`), `auth.ts` (password/cookie auth — see below), `llm.ts` (optional LLM assist — see below), `suggestions.ts` (harness-agnostic synthesized next-prompt suggestions — see below), `turnRouter.ts` (where a settled turn goes — see below), `autopr.ts`/`prAgent.ts`/`git.ts` (the auto-PR capability), `continuity.ts` (Continuity Mode), `adapters/` (harness boundary, incl. `shell-integration/` injected rc scripts), `sessions/manager.ts` (PTY/streaming/lifecycle + session-event fan-out, harness-agnostic), `commands.ts` (lists cwd executables + `$PATH` + shell aliases + recent/frequent commands from the DB command log; PATH/alias cached 30s), `files.ts` (file-editor backend: list subfolders / read / write, every path confined to a folder root), `browse.ts` (add-folder picker backend — see below), `system/` (System state telemetry — see below), `chatLog.ts` (chat render log capture — see below), `paths.ts` (`expandHome` — see below), `db.ts` (SQLite: folders, users, auth sessions, command log, resumable chat sessions, chat render log), `index.ts` (HTTP + WS + dev Vite).
- **Session ↔ folder membership:** `SessionInfo.folder` (launch cwd, fixed for the session's life) is the *only* thing sessions are grouped by — `App.tsx`'s `sessionsInFolder`, the auto-select-new-session effect, `manager.sessionFolder` (folder-recency bumps), `chat_sessions.folder`. **`SessionInfo.cwd` is live and drifts with every `cd`** (shell integration) and is display/logging only (`sessionCwd` → command log, session-row subtitle). Grouping by `cwd` was a real bug: `cd` out of the launch folder made the session vanish from the UI (its cwd matched no known folder, while it stayed running and mounted), then re-attach itself to whatever folder was *added later* at that path. Membership must never depend on mutable state. The active-tab pin (`activeSession[folder]`) is likewise validated against the folder's own tabs before use — terminals are all mounted at once and shown purely on an id match, so a foreign pin paints another folder's session over an empty tab list.
- **Folder path normalization (`server/paths.ts`):** a folder path is an *identity* (the `folders` primary key, and what `SessionInfo.folder` is compared against to group a session under its folder), so it has exactly one spelling: `normalizeFolder` = `expandHome` + a guaranteed trailing slash. Two spellings of one folder = two list entries that drift apart, each with its own sessions/command history.
  - `expandHome` expands a leading `~`/`~/…` (never `~user/…`, needs a passwd lookup). `~` is shell syntax — Node's `fs`/`spawn` treat it as a literal directory name, so a folder typed as `~/src/foo` never resolves (nothing to do with the service user: it's a systemd *user* service, so `HOME` is already the installing user's).
  - Applied at the WS entry points in `index.ts` (`start` cwd, `addFolder`, `removeFolder`) so the allowlist / session cwd / `/api` cwd params see one form — **and again inside `db.ts`'s `upsertFolder`/`removeFolder`**. The DB one is load-bearing, not belt-and-braces: one un-normalized write anywhere forks the folder (this is exactly how a `~` row bred a duplicate — opening it upserted the *expanded* session cwd as a second row). **Normalize at the persistence boundary, never per call site.**
  - `manager.ts` normalizes the shell-integration `cwd` event too — a shell reports `/x/y` where the folder key is `/x/y/`, which would drop a session out of its own folder tab.
  - `db.ts` `migrateFolderPaths()` (runs at import, idempotent) folds legacy rows into canonical form: merges into an existing canonical row keeping the newer `last_used_at`, and for `~` rows re-points `chat_sessions.folder` / `commands.cwd` / `chat_render_log.cwd` (slash-only fixes don't re-point — those columns hold live cwds, incl. subdirectories, whose trailing slash is their own).
  - Client-side, `submitNewFolder` never predicts the stored path: it defers selection (`pendingFolderSelect`) to the next `folders` broadcast, where the add sorts first.
  - **Display is the other half:** storage is canonical/absolute, but the UI shows paths home-relative (`~/src/x/`). The `folders` server message carries `home` (server `$HOME`) alongside the list — the browser can't know it — and `web/paths.ts` `displayPath(path, home)` renders it (folder list + folder header; `title=` keeps the absolute path). Home *itself* is the exception — it stays absolute (`~/` alone names nothing) and `folderName(path, home)` labels it "home" rather than the account name. Display only: every path sent back to the server is the stored one. Pure coverage `web/paths.test.ts`.
- **Add folder (folder picker):** the sidebar's "+ Add" opens `FolderPicker.tsx`, a modal filesystem browser (reuses the `.resume-*` dialog shell) mounted at app level in `App.tsx` — adding a folder must work with none open. **The text field is the source of truth; the tree is a view of it** (ancestors auto-expanded, best prefix match highlighted), and every tree interaction writes back into the field, so typing/Tab/tap all converge on one string. Typed text splits at the last `/` into a directory (listed) + a partial name (prefix-filters its subfolders, case-exact first); ↑/↓ move the highlight, Tab completes it into the field with a trailing `/`, Enter adds (or, when the partial isn't a real folder but prefix-matches one, completes instead). **A nonexistent path is created**: once the parent listing proves it missing the button reads "Create" and the server's `addFolder` does `mkdirSync(path,{recursive:true})` *before* `upsertFolder` (a failed mkdir adds nothing; the error only reaches the console). Path text logic is pure in `web/folderPath.ts` (`splitTyped`/`toAbsDir`/`toTyped`/`parentOf`/`rootFor`/`chainFrom`/`matchEntries`, tested in `folderPath.test.ts`): display keeps `~/` (here home itself collapses too, unlike `displayPath`) while tree keys and requests are canonical absolute paths, and the tree roots at home when the path is inside it (else `/`). Backend is `GET /api/browse?path=` → `server/browse.ts` `browseDirs` (auth'd; `~`/empty = home; directory *names* only, symlinked dirs followed, 1000-entry cap with `truncated`, fs errors mapped to readable text). Deliberately **not** folder-allowlisted, unlike `/api/files` — you're picking a folder that isn't known yet, and typing a path by hand always reached just as far. Submitting still sends the raw text: the server normalizes it (`normalizeFolder`) and `pendingFolderSelect` adopts whatever it stored.
- `web/` — React app. `client.ts` (WS client, per-session output buffering + per-session `ChatState`, sticky Ctrl modifier applied in `input()`), `auth.ts` (client-side auth helpers), `Login.tsx` (login/signup gate), `TerminalView.tsx` (xterm per session), `ChatView.tsx` (chat-bubble view for `ui:"chat"` sessions, lazy-loaded, bundles `marked`), `FileEditor.tsx` (the file-editor tab: file picker + CodeMirror, lazy-loaded), `SystemState.tsx` (the System state page, lazy-loaded — see below), `App.tsx` (workspace + mobile keyboard key-bar + editor-tab bookkeeping + AI-assistant mode toggle), `CommandBuilder.tsx` (the `./` command-builder dialog), `FolderPicker.tsx` + `folderPath.ts` (the add-folder browser — see below), `commandCatalog.ts` (static well-known-command subcommand/flag data + curated common-command list), `styles.css`. Becoming the active tab focuses that session's input (xterm / chat composer) so it's typeable at once; while an exited session is active, Enter/Escape trigger "Close session" (`App.tsx` window keydown, suppressed while a dialog is open).
- **Last view (server-persisted, per user):** which folder + tab you were on survives a reload and follows you across devices. `ViewState {folder, sessionId}` (`shared/protocol.ts`) ↔ `user_views` table (one row per user, folder normalized in `setUserView` like every other folder column) ↔ `GET/PUT /api/view` (auth'd, keyed by `authedUser`). **Load-time only, deliberately not over `/ws`** — a live broadcast would yank an open laptop tab around when you tap something on your phone. `App.tsx`: fetch on mount → `storedView` ref; a one-shot restore effect waits for `viewFetched` + `snapshotSeen` (the first WS `sessions` message; the server sends `folders` before it) so ids can be validated. **`client.onSessions`/`onFolders` replay their current value synchronously on subscribe**, so the connect effect's `replaying` flag ignores that first (empty) call — counting it as the snapshot made the restore run against an empty folder list and silently fall through to the default every time. The restore is also ordered *after* the auto-select-new-session effect, which treats the whole first batch as new and would otherwise win. `viewRestored` gates both the "default to most-recent folder" effect (else it races the stored folder) and the debounced save (else the default overwrites what was stored). Stale ids just fall back to the folder's default tab — sessions die, and editor tabs are client-only so their ids never survive a reload.
- **Chat sessions (pi + claude):** `SessionInfo.ui` is `"terminal" | "chat"`, declared by the adapter. Two adapter shapes drive chat, both harness-confined; the manager just folds their `ChatEvent`s into per-session `ChatState`:
  - **`createChatTranslator()` (pi)** — manager spawns the agent **piped, no PTY** (`child_process.spawn`); the `ChatTranslator` maps wire format ↔ schema (`push(stdout) → ChatEvent[]`, `encode(ChatAction) → stdin bytes + synthetic events`). pi runs `pi --mode rpc` (JSONL, manual `\n` framing, never readline — U+2028/29). ALL pi vocabulary in `adapters/pi.ts`.
    - **Model switcher.** `init()` sends three queries (`get_commands` + `get_available_models` + `get_state`); their replies feed the *same* harness-agnostic `models`/`model-changed` events + `set-model` action claude uses, so **`ChatView`/protocol/reducer needed no change at all**. Three things the wire forces, all verified live:
      - **pi's RPC replies are NOT ordered against their requests** (a `get_state` came back ahead of a `set_model` sent before it). So the translator holds `currentModel` itself and restates it in the `models` event — the reducer's `models` fold overwrites `currentModel` wholesale, so a catalog landing after `get_state` would otherwise blank the selection. The **date is hardcoded ISO order** (locale-independent, unambiguous, sorts); the **time is localized** via `displayLocale`, since that's the half carrying the 12h/24h convention. Three things it must keep doing: build the date from **local** getters (`toISOString()` is UTC and names the wrong hour), **floor** the coarse unit (23h59m reads `23h`, not `24h` a minute before the day form), and zero-pad. `now`/`locale` are injectable so the format is testable without a `navigator`; the tests build both sides from local components and so pass in any TZ.

A deliberate personal heuristic, not a general truth (it assumes English is the language of *work*), and it picks a **locale, not a clock** — a 12-hour home locale like `ko-KR` still formats 12-hour. Two invariants: match English **exactly** (`=== "en" || startsWith("en-")` — `enm`/`enq`/`eno` are their own languages, and a primary subtag ends at the first hyphen), and **validate the tag it returns** via `supportedLocalesOf` (malformed → throws, well-formed-but-unsupported → `[]`; an unvalidated tag reaches `toLocale*String` and throws mid-render). Pure coverage `web/time.test.ts`.

- **Resume (chat sessions):** harness-agnostic via an opaque "resume key". `SessionOptions.resume` (input) → adapter restores prior state; `ChatSessionHandlers.onResumable(key)` (output) → manager persists it. Both **claude** and **pi** implement resume; **terminal** ignores it. Two mechanisms by adapter shape:

- **Composer draft (server-side, harness-agnostic):** the unsent prompt lives in `ChatState.draft`, so a reload / folder detour / other device doesn't lose half-written text (the chat analogue of a terminal's unsubmitted line sitting in the PTY — terminals need nothing). `set-draft` `ChatAction` → handled by `manager.ts` itself like `set-assistant` (never an adapter) → `draft` `ChatEvent` → reducer. Text only; attachments stay client-side. Not persisted to SQLite — a server restart kills the session anyway.

A prompt sent is a draft spent; don't reintroduce a conditional clear (an earlier prefix-match rule tried to protect text typed *after* Send, since `index.ts` resolves prompt images async and so applies an image prompt *after* later `set-draft`s — that window is worth less than the simple rule, and `ChatView` keeps the local draft authoritative anyway).

- **Rewind (claude only):** jump the conversation back to an earlier **user** prompt — it and everything after it leave the transcript *and* the model's context; the agent is interrupted; the prompt goes back into the composer for re-sending. Gated by `ChatState.capabilities` (`ChatCapabilities {rewind?, rewindFiles?}`, a `capabilities` event emitted at session start), so pi shows none of it and needs no changes. **Manager/`index.ts` are untouched** — `rewind`/`rewind-preview` are `ChatAction`s that pass straight through to `chatSession.action`, and the adapter emits the resulting `rewind`/`rewind-preview` events itself.

Model/mode are tracked on the instance so the relaunch keeps the user's picks. Deriving it from `init` alone made *resume → rewind before the first prompt* fail with "session not ready" (the common case: reopen a tab, undo the last turn) and left the stale key persisted; both are pinned by e2e tests.

- **System state page (host/GPU/LLM/docker telemetry):** a single sidebar link **above** Folders opening a folder-independent, read-only page of cards — System usage, GPU usage, LLM usage, LLM tokens, Docker, Disk, Network. A base `button,input,select,textarea { border: none }` reset makes borderless the floor; never rely on merely deleting a rule. `select` additionally needs `appearance: none` (it otherwise draws native bevelled chrome and ignores background/border), which costs the dropdown arrow — redrawn by `.chat-menu-btn::after` (and `.assistant-select::after`) as a **mask** filled with `var(--muted)` so it follows the palette (a `background-image` SVG would hardcode the colour, and a `background:` shorthand on the select would wipe it). No protocol change, no second copy of the transcript, no interaction with the 200-message cap or `rewind`'s agent pruning — which is why this is preferred over synthesizing an `agent-start`/`agent-event` stream (that would also need a fake tool part to hang the panel on, i.e. claiming the *agent* called a tool the pipeline actually ran). Consequences: `AgentPanel` takes a plain `ChatState` (not an `AgentRun`) and renders `streaming` too — a live panel would otherwise stay empty until the turn ended; only the **first** trace naming a given session hosts the panel (`inlineTraceSession`, render-time like `groupParts` — a run posts several notes about the same session and they'd all show the identical live transcript); it auto-expands once on the peer going `busy`, **not** on it having messages, or a reload would pop open every historical PR note; and it outlives the tab: gated on `heldSessions` (listed + hidden), not `knownSessions`, so closing the `/pr` tab drops only the chip — the panel goes when the parent session is removed (which hard-removes the child).

This app's own agent always ends a server change that way (it may never restart the service itself), so without the rule every such turn was declined.

Flag set server-side, never inferred from `kind`+`outcome` (a continuity-only decline carries `kind:"auto-pr"` too).

Skipped when the branch already tracks an upstream: its name may carry an open PR. **2. commit** — `git add -A` then up to 3 `suggestCommitMessage(stagedDiff)` attempts (each rejection fed back so the retry doesn't repeat it), validated by `sanitizeCommitMessage`, falling back to `auto-pr: update N files`. **3. push** — `git push -u origin <branch>`. **4. PR** — `prAgent.ts`, **unless the branch already has an open PR** (`git.ts` `openPrForBranch` → `gh pr list --head <branch> --state open`): a branch keeps its PR across turns, the step-3 push already updated it, and running `/pr` again would duplicate it or just fail. The existing `{number,url}` is adopted so step 5 can still merge it. `parseOpenPr` (pure, tested) reads the `--json` output; **`[]` (no PR) and unusable output both yield `null`** → fall through to creating one, i.e. missing/unauthenticated `gh` degrades to the pre-existing behaviour rather than silently never opening PRs. Merged/closed PRs don't count, so a reused branch can get a fresh one. **5. merge** and **6. back to main** (`git checkout <base>` + `git pull --ff-only`) run **only when `autoMerge` is ticked**; merge is `gh pr merge <n> --squash --delete-branch`. **7.** a landed merge then calls `runContinuity(ctx, {afterPr:true})` — a no-op when continuity is off, and the moment the `after-pr` new-session policy keys off; it runs inside the router's single-flight with the anchor still pinned, so it can't race a settle of its own. The pure `decideFlow({dirty,onMain,diffVsBase})` picks between `commit` / `pr-only` (clean branch that already diverges — push + PR, no new commit) / `nothing` (clean and matching the base — skip to step 6 regardless of `autoMerge`).

## What this is

- Harness-agnostic web remote for AI coding agents.
- Single webpage to manage local agent sessions: Claude Code + pi first, other CLI harnesses later.
- User-facing overview: `README.md`.

## Architecture (settled)

- **Frontend:** React + Vite. Renders sessions, streams output, sends input back.
- **Backend:** Node. Spawns each agent as a **local subprocess in a PTY** (`node-pty`), supervises lifecycle, streams raw terminal I/O to the browser via WebSocket.
- **Terminal:** browser renders sessions with **xterm.js**; keystrokes/resize go back over `/ws`. One persistent xterm per session (hidden when inactive) so scrollback survives tab switches.
- **Single port:** UI, `/api`, and `/ws` all listen on one port (default 4000). Dev embeds Vite in **middleware mode** in the Node server (`--dev` flag, not env); prod serves `dist/web`. `/ws` and Vite HMR coexist via `noServer` + manual `upgrade` routing.
- **Harness adapters:** core abstraction. An adapter describes *how to invoke* an agent (`HarnessInvocation`: command/args/env) plus optionally how to translate its protocol (`createEventParser` for PTY event markers, `createChatTranslator` for chat sessions); all process/streaming/lifecycle is harness-agnostic in `sessions/manager.ts`.
- **Hard constraint:** keep harness-specific logic confined to adapters. UI/session-mgmt/LLM features stay harness-agnostic. New agent = new adapter, never UI/core changes. Leakage into shared code = design smell.

## Config

- No env variables. All config lives in `config.json` (gitignored).
- `config-gen.sh` runs a setup dialog to generate `config.json`. Shape in `config.example.json`.
- Keys: `harnesses` (per-harness `enabled`/`command`, optional `env` for the process — used by `claudeLocal`), `llm` (`provider`/`baseUrl`/`model` for the optional LLM assist — see above), `autoPr` (optional `harness`/`instructions` for the auto-PR session, default `pi` + `/pr`; written by `config-gen.sh`), `tokenUsage` (optional `file`/`pricing` for the System page token card), `users` (enabled logins, live-reloaded), `registration` (`open`/`closed`, default closed), `server.port`.
- Never reintroduce `process.env`-style config or `.env` files.

## LLM features

- **Built:** AI-assistant mode — auto-answering chat permission/question dialogs, synthesized next-prompt suggestions, auto-PR (LLM-written branch name / commit message, plus supervision of the headless PR session), and Continuity Mode (routing each settled turn, then writing and sending the next prompt) via an OpenAI-compatible endpoint (`server/llm.ts`; see the LLM-assist bullet in Layout).
- **Planned (not built):** session summaries, natural-language task routing, notification/triage.
- All layered on the harness-agnostic core; consume the common session interface; must not depend on a specific harness.
